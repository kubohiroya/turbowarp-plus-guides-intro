13.1 Write tests inside a project

A test repeats a claim: after this operation, this result should follow. It helps detect regressions when a project changes, separately from playing the project on its normal stage.

  1. Add TurboWarp-Test from the official catalog.
  2. Place a named test hat on the sprite or Stage being checked.
  3. Prepare inputs, run the behavior, then compare actual and expected values with assertion blocks.

For example, “score after awarding points” sets the score to zero, calls the award routine once and checks that the score is ten. Give separate names to different inputs, boundary cases and failure cases so the results explain what broke.

A target's “before tests” hat can perform shared setup. Only one setup hat is allowed per sprite or Stage. Green-flag scripts do not run automatically, so initialize test inputs in setup or the test itself. See the TurboWarp-Test guide for its blocks.

13.2 Run tests in their own view

  1. Choose Open test run view from the stage display menu (▼).
  2. Check the list. Use Run all for every test or a test's Run button for one.
  3. Watch the dedicated stage and status. Use Stop to interrupt the run.

A run uses a copy of the project captured when you start it. Normal manual test runs do not require saving a file first. After editing code, run again to obtain a result for the new code; an earlier result does not validate later edits.

If no tests are listed, check for TurboWarp-Test test hats rather than only ordinary event hats. See also the stage display menu.

13.3 Inspect failed values and blocks

StatusMeaning and next step
PassedThe script ended without a failing assertion. Also check that the assertions actually cover the intended behavior.
FailedAn assertion did not match. Compare expected and actual values.
Timed outSetup or the test exceeded its frame limit. Review termination conditions and waits.
ErrorDuplicate setup hats or an exception prevented execution. Read the reason shown.

Show block opens the relevant sprite or Stage and centers the failed assertion. If you deleted or recreated the block after a run, rerun the test so the result corresponds to current code.

Results may include identifiers for the tested extension builds. Rerun after updating an extension to check its new build.

13.4 Understand the relationship to your editor

Each test reloads the project copy in a dedicated VM. The test does not operate the editor VM, selected sprite or code undo history. State changed by one test is not carried into the next, so each can have independent setup.

The runner disables compilation and does not press the green flag. A passing run does not establish identical behavior for normal green-flag execution, graphics, sound, input or external communication. Check these with ordinary execution and the debugger where needed. A copied project does not make external service access a mock.

The default limit is 3000 frames. A frame counts runner steps, not seconds or a fixed amount of wall-clock time.

13.5 Use tests while editing and developing extensions

Make a small change, run related tests, fix failures, then save, inspect the diff and commit. Test blocks are part of the project and can be saved with the SB3 or project folder.

The test package also provides a JUnit XML API for CI, but the Editor view described here has no JUnit download action. CI integration is a developer task. Checks of a saved Git generation are also distinct from these manual runs of the current editor project.
