13.1 作品の中にテストを書く

テストとは「この操作をしたら、この結果になる」を繰り返し確かめるスクリプトです。作品を改良したとき、今まで動いていた処理が壊れていないかを調べられます。通常の実行画面で遊ぶ操作とは分けて実行します。

  1. 公式カタログから TurboWarp-Test を追加します。
  2. 調べたいスプライトまたはステージに、テスト名を付けたテストハットを置きます。
  3. 入力値を用意し、調べたい処理を実行し、拡張の確かめるブロックで実際の値と期待する値を比べます。

たとえば「加点後の得点」というテストで、得点を0にし、加点処理を1回呼んで、結果が10かを確かめます。別の入力・境界値・異常時も、それぞれ名前を付けたテストにすると、何が壊れたかを探しやすくなります。

共通の準備は同じ対象の「テストの前に」ハットに書けます。1つのスプライト・ステージに置ける準備ハットは1つです。緑の旗の初期化処理は自動実行されないため、テストが必要とする初期値は準備かテスト自身に書きます。ブロックの詳細はTurboWarp-Testのガイドを参照してください。

13.2 専用のテスト実行画面で動かす

  1. 実行画面の表示メニュー（▼）から「テスト実行画面を開く」を選びます。
  2. 作品のテスト一覧を確認します。「すべて実行」で全件、各テストの「実行」で1件を実行します。
  3. 実行中は専用の実行画面と状態を確認します。中断するには「止める」を押します。

実行を始める時点の作品の写しを使います。通常のテスト実行の前にファイル保存を必須とする機能ではありません。実行後にコードを直した場合は、もう一度実行して新しい結果を確認してください。古い結果が自動的に新しいコードの証明になるわけではありません。

「この作品にはテストがありません」と出たら、通常のイベントハットだけでなくTurboWarp-Testのテストハットがあるかを確認します。メニューやパネルの配置は実行画面の表示メニューも参照してください。

13.3 失敗した値とブロックを確認する

状態意味と次の操作
成功スクリプトが終わり、失敗した確かめるブロックがありません。期待する振る舞いを本当に確かめているかも見直します。
失敗確かめるブロックで不一致がありました。期待・実際の値を比べます。
時間切れフレーム上限内に準備やテストが終わりませんでした。終了条件や待機を見直します。
エラー準備ハットの重複や実行時の例外などで動かせませんでした。表示された理由を確認します。

失敗した項目の「ブロックを表示」を押すと、該当するスプライト・ステージのコードを開き、失敗した確かめるブロックへ移動します。対象のブロックを消したり作り直したりした後は、現在のコードに対応するよう再実行してください。

結果にはテスト対象の拡張ビルドの識別情報が含まれる場合があります。拡張を更新した後は、新しいビルドで再実行して結果を確認します。

13.4 編集中の作品とテストの関係を理解する

各テストは専用のVMに作品の写しを読み込み直して動かします。編集中のVM、選んだスプライト、コードの取り消し履歴をテスト用に操作しません。前のテストが変えた変数やスプライトの状態を次のテストへ引き継がないため、テスト同士が独立した準備を持てます。

専用実行ではコンパイラーを使わず、緑の旗も押しません。普段の緑の旗での動作、表示・音・入力・拡張の外部通信まで同じ条件で検証したことにはなりません。必要な場面は通常の実行やデバッガーでも確かめてください。作品をコピーしても、外部サービスへのアクセスが模擬になるわけではありません。

既定の上限は3000フレームです。ここでのフレームは実行器の処理回数で、3000秒や一定の実時間を意味しません。

13.5 編集・Git・拡張づくりに組み込む

小さく修正し、関連するテストを動かし、失敗箇所を直してから保存・差分確認・コミットへ進むと、変更の理由と確認内容を結び付けられます。テストのブロックも作品の一部なので、SB3や作品フォルダに保存して一緒に管理します。

テストパッケージにはCI向けのJUnit XML出力APIもありますが、この章で説明するEditorの実行画面にJUnitファイルのダウンロード操作はありません。CIへの接続は開発者向けの組み込み作業です。Gitの保存世代に対する検査と、ここでの編集中の作品に対する手動実行も区別してください。
